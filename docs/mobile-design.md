## 一、项目背景与目标

### 1.1 项目背景

华溯计量管理系统（hs2.0）是面向计量检测/校准行业的 LIMS 系统，目前由两个子系统组成：

- `netcore/` — 后端 API 服务（.NET Core 2.2 + Dapper + 自研 ORM）
- `p-admin/` — 前端管理界面（Vue 2 + HeyUI + Webpack 3）

现有前端为**桌面端优先**设计，存在以下移动端痛点：

1. **审批流程移动化缺失**：审核员/审批员外出时无法及时处理待办，影响单据流转效率
2. **审核界面不适配移动端**：核心审核功能采用三栏分屏布局（列表 + 证书预览 + 记录表单），移动端无法使用
3. **客户查询体验差**：现有外部查询页面虽做了部分移动适配，但体验仍可优化
4. **缺少扫码能力**：现场检测、样品关联、证书验证场景缺少移动端扫码入口
5. **缺少推送通知**：审批待办仅靠 5 分钟轮询，实时性不足

### 1.2 设计目标

| 目标 | 说明 |
|------|------|
| **审批移动化** | 让审核员/审批员随时随地处理待办，缩短单据流转周期 |
| **查询移动化** | 业务数据随时可查（委托单/受理单/证书/费用/物流） |
| **客户自助化** | 客户可自助查询检测进度、验证证书真伪、查看物流 |
| **现场便捷化** | 利用扫码、拍照能力，提升现场作业效率 |
| **后端零改造** | 完全复用现有 ORM 元数据驱动 API，不新建后端服务 |

### 1.3 设计原则

| 原则 | 说明 |
|------|------|
| **轻量化** | 移动端不做大而全，聚焦高频、移动场景优先的功能 |
| **场景驱动** | 以"谁在什么场景下需要什么"来划分模块，而非照搬桌面端菜单 |
| **复用后端** | 共用现有 `api/Data/call/{Module}/{ApiCode}` 接口体系 |
| **渐进式** | 一期核心功能（MVP），二期扩展，三期完善 |
| **做减法** | 原始记录编辑、Word 模板编辑、系统管理等桌面端专属功能不在移动端实现 |

## 二、现有系统分析

### 2.1 现有业务模块全景

系统共 45 个路由模块，按业务划分为 6 大区：

| 业务区 | 模块数 | 核心功能 |
|--------|--------|----------|
| **b01 基础管理** | 12 | 委托单位、规程项目、标准器、部门、员工、资质证书、人员授权、培训、能力确认、分包、人员监督 |
| **r01 检验管理** | 8 | 项目管理、原始记录、委托审核、委托审批、费用管理、受理单、委托管理 |
| **r02 统计报表** | 4 | 检测情况统计、人员效能、客户统计、物流管理 |
| **s01 系统管理** | 13 | 资源管理、模块管理、功能管理、角色管理、用户管理、字典、模板、记录模版、日志、文件、公式、Word 模版、SQL 配置 |
| **out 外部服务** | 5 | 受理查询、证书核验、电子证书验证、物流查询 |
| **独立业务** | 4 | 采购订单、零售退货 |

### 2.2 核心数据流（复用基础）

所有数据操作通过统一入口：

```
前端调用
  → POST api/Data/call/{ModuleName}/{ApiCode}
  → DataController.Call
  → MOUDLE.Open(ModuleName) 加载模块配置
  → MD.GetAPI(ApiCode) 获取接口配置
  → switch(APITYPE) 路由到 doQuery/doOpen/doSave/doDelete/...
  → SchemaManage.GetResource(resourceName) 加载元数据
  → BuildSQL01 构建SQL
  → ViewOperate01 执行SQL (事务)
  → 返回 QueryResult/DataView/void
```

**这意味着移动端只需对接同一套接口，无需任何后端改动。**

### 2.3 现有用户角色体系

通过 `v-per` 指令 + `tss_funcpoint` 权限点实现细粒度权限控制：

| 角色 | 核心权限点 | 移动端需求 |
|------|-----------|-----------|
| 系统管理员 | s01/* 全部 | 移动端不做 |
| 业务操作员 | LI_M02/A04(修改)、A17(提交) | 待提交、提交操作 |
| 复核员 | LI_M02/A12(复核)、A13(撤销复核) | 待复核列表、复核操作 |
| 审批员 | LI_M02/A14(审批)、A15(撤销审批)、A16(驳回) | 待审批列表、审批操作 |
| 证书管理员 | LI_M02/A21(生成证书)、A55(电子签章) | 待签发、签章操作 |
| 收费员 | LI_M03/A04(收费) | 费用确认 |
| 客户(外部) | 无需登录 | 进度查询、证书验证 |
| 管理层 | LI_M02/A14、报表查看 | 审批、统计概览 |

### 2.4 现有移动端适配现状

| 现有页面 | 移动适配 | 复用价值 |
|----------|----------|----------|
| `/out/ecert` 电子证书验证 | ✅ 已适配（max-width:600px） | ⭐⭐⭐ 高，可作为参考 |
| `/out/logistics` 物流查询 | ✅ 已适配（max-width:700px） | ⭐⭐⭐ 高 |
| `/out/m01` 检测进度查询 | ⚠️ 部分适配 | ⭐⭐ 中 |

## 三、用户角色与移动场景

### 3.1 场景矩阵

| 角色 | 核心移动场景 | 频率 | 优先级 |
|------|-------------|------|--------|
| 检测/校准人员 | 查看待办任务、提交原始记录、扫码关联样品 | 每日多次 | ⭐⭐⭐ |
| 复核员 | 收到待复核通知、快速复核/驳回 | 每日多次 | ⭐⭐⭐ |
| 审批员 | 收到待审批通知、快速审批/驳回 | 每日1-3次 | ⭐⭐⭐ |
| 证书管理员 | 证书签发提醒、电子签章 | 每日1-2次 | ⭐⭐ |
| 业务受理员 | 受理登记、委托单查询、物流登记 | 每日多次 | ⭐⭐⭐ |
| 客户(外部) | 查检测进度、验证证书、查物流 | 按需 | ⭐⭐⭐ |
| 管理层 | 看统计报表、审批、公告 | 每日1-2次 | ⭐⭐ |
| 系统管理员 | 用户管理、权限配置 | 偶尔 | ⭐ |

### 3.2 典型用户旅程

**场景 A：审批员外出时处理待办**

```
收到微信推送通知
  → 打开小程序
  → 工作台显示「待审批 3 件」
  → 点击进入待审批列表
  → 选择一条原始记录
  → 查看基本信息 + 证书预览
  → 点击「通过」，输入审批意见
  → 完成，列表刷新
```

**场景 B：客户查询检测进度**

```
扫描小程序码 / 打开 H5 链接
  → 输入委托单号 + 手机号（或扫码）
  → 查看检测进度列表
  → 点击查看证书
  → 下载 PDF 证书
```

**场景 C：检测员现场扫码**

```
打开扫码功能
  → 扫描样品条码
  → 自动跳转委托单详情
  → 查看检测项目和状态
```

## 五、技术方案选型

### 5.1 方案对比

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **uni-app** | 一套代码多端运行(小程序+H5+App)、Vue 生态、扫码能力 | 性能略差、复杂交互受限 | ⭐⭐⭐ |
| **微信小程序原生** | 性能最优、扫码/推送原生支持、用户基数大 | 仅限微信、需审核 | ⭐⭐⭐ |
| **H5 响应式** | 开发快、复用现有前端、无需安装 | 体验差、无推送、无扫码 | ⭐⭐ |
| **原生 App** | 体验最好、功能最全 | 开发成本高、需双端开发 | ⭐ |

### 5.2 推荐方案：uni-app（Vue 3 + 微信小程序 + H5）

**选型理由**：

1. **Vue 生态契合**：现有前端团队熟悉 Vue，学习成本低
2. **多端输出**：一套代码同时输出微信小程序 + H5，覆盖最大用户群
3. **扫码能力**：uni-app 封装 `uni.scanCode`，一套 API 多端调用
4. **推送通知**：小程序模板消息可推送审批提醒（H5 端用 Web Push 或短信）
5. **后端复用**：直接调用现有 `api/Data/call/{Module}/{ApiCode}` 接口
6. **UI 组件库**：uni-ui + uView UI 提供丰富的移动端组件

### 5.3 技术栈

| 层级 | 技术选型 | 说明 |
|------|----------|------|
| 框架 | uni-app + Vue 3 | Composition API，更现代 |
| 状态管理 | Pinia | 替代 Vuex，更简洁 |
| UI 组件库 | uView UI 2.x | 移动端组件齐全 |
| 请求库 | uni.request 封装 | 原生能力，兼容多端 |
| 样式 | SCSS + rpx | 响应式单位 |
| 构建工具 | Vite (uni-app 内置) | 快速构建 |
| PDF 预览 | uni-app PDF 插件 / iframe | 证书预览 |
| 扫码 | uni.scanCode | 多端扫码 |

## 十、关键设计决策

### 10.1 审批流程移动端适配

桌面端审核是**三栏分屏**（列表 + 证书预览 + 记录表单），移动端改为**分步式**：

```
桌面端：[列表 | 证书预览 | 记录表单]  ← 三栏并排

移动端：列表 → 详情卡片 → 证书预览 → 操作  ← 分步串联
```

### 10.2 API 复用策略

移动端直接复用现有 `api/Data/call/{Module}/{ApiCode}` 接口：
- 认证：复用 IdentityServer4 JWT Token
- 数据查询：复用 ORM 元数据驱动的 query/open API
- 审批操作：复用 flowSave (A12/A14/A16 等)
- **不需要新建任何后端接口**

### 10.3 权限控制

复用现有 `tss_funcpoint` 权限体系：
- 登录后调用 `C00/A04` 获取菜单
- 调用 `C00/A06` 获取功能权限点
- 根据权限点控制页面和按钮显示（对应桌面端 v-per 指令逻辑）

### 10.4 客户端（外部访问）

- 微信小程序：通过小程序码分享给客户
- H5：现有 out/ 模块优化为移动端友好的响应式页面
- 无需登录，保持现有 OuterController 接口

### 10.5 移动端 vs 桌面端功能边界

| 功能 | 桌面端 | 移动端 | 说明 |
|------|--------|--------|------|
| 原始记录编辑 | ✅ 完整编辑 | ❌ 不做 | 需要 OnlyOffice，移动端不适合 |
| Word 模板编辑 | ✅ OnlyOffice | ❌ 不做 | 同上 |
| 审批操作 | ✅ 三栏分屏 | ✅ 分步卡片 | 移动端简化交互 |
| 批量审批 | ✅ 勾选列表 | ✅ 简化版 | 移动端支持 |
| 业务查询 | ✅ 高级筛选 | ✅ 简单搜索 | 移动端简化筛选 |
| 统计报表 | ✅ 完整图表 | ✅ 简化概览 | 移动端只看关键指标 |
| 系统管理 | ✅ 完整 | ❌ 不做 | 管理操作在桌面端完成 |
| 扫码功能 | ❌ 无摄像头 | ✅ 原生扫码 | 移动端独有 |
| 推送通知 | ❌ 无推送 | ✅ 小程序消息 | 移动端独有 |
| 物流登记 | ✅ 表格录入 | ✅ 扫码 + 拍照 | 移动端更便捷 |
| 证书验证 | ✅ 网页验证 | ✅ 扫码验证 | 移动端更便捷 |

## 十一、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 微信小程序审核周期 | 影响发布 | 提前准备资质材料，使用体验版给内部测试 |
| OnlyOffice 在移动端不可用 | 证书预览受限 | 改用 PDF.js / iframe 预览 PDF，不走 OnlyOffice |
| 接口跨域（CORS） | H5 端请求失败 | 后端配置 CORS，或使用 H5 代理 |
| Token 安全 | 越权风险 | Token 加密存储，定期刷新，HTTPS 传输 |
| 网络不稳定 | 操作失败 | 关键操作（审批）增加重试机制和离线缓存 |
| 批量审批误操作 | 数据错误 | 增加二次确认弹窗，操作不可撤销需提示 |

  const token = uni.getStorageSync('token')
  return uni.request({
    url: BASE_URL[type] + `${moduleName}/${apiCode}/`,
    method: 'POST',
    header: {
      'Authorization': 'Bearer ' + token,
      'Content-Type': 'application/json'
    },
    data: params
  })
}
